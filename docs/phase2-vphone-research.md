# Phase 3 environment research, performed before Phase 2 implementation

Reviewed 2026-10-01. Upstream source snapshot: `67d0734a6f5ef960b9a12320b216e73d6491ed18`. This is read-only research; no vphone binaries, firmware, tools or security modifications were installed. Source observations are in `evidence/phase2/vphone-research.json`.

**DOCUMENTED:** vphone-cli runs a virtual iPhone using Apple's Virtualization.framework and PCC research infrastructure. Its current public workflow uses patched/jailbreak firmware. It is neither Catalyst nor the Xcode Simulator. [Overview](https://github.com/Lakr233/vphone-cli/blob/67d0734a6f5ef960b9a12320b216e73d6491ed18/README.md), [research index](https://github.com/Lakr233/vphone-cli/blob/67d0734a6f5ef960b9a12320b216e73d6491ed18/Research/README.md).

**DOCUMENTED:** the upstream compatibility table records iPhone17,3 iOS 27.0 build 24A435 paired with cloudOS 26.4 build 23E5207q, reaching the lock screen and answering the control daemon. This is upstream boot evidence, not our runtime's execution evidence or proof of an unmodified physical-device kernel. [Compatibility](https://github.com/Lakr233/vphone-cli/blob/67d0734a6f5ef960b9a12320b216e73d6491ed18/Documents/Guides/compatibility.md).

**DOCUMENTED:** upstream research describes debugserver entitlement edits and a paravirtual GPU driver sourced from PCC/cloudOS, with additional compiler support. These make debugging and GPU experiments plausible; they do not establish our ability to attach a debugger or run our Metal compute case. The research inventory contains historical variants and differs from some current guide descriptions: record the actual installed version, resolved patch manifest and firmware hashes when testing. [Patch inventory](https://github.com/Lakr233/vphone-cli/blob/67d0734a6f5ef960b9a12320b216e73d6491ed18/Research/0_binary_patch_comparison.md).

**DOCUMENTED:** the host guide requires research-guest permission, relaxed SIP debugging restrictions and privileged AMFI authorization for the entitled VM executable (or a more permissive alternative). These conflict with the Phase 2 instruction to preserve security settings. Phase 2 performs no setup. Phase 3 needs an explicit host-policy decision rather than silently treating a jailbreak VM as an ordinary supported development install. [Host setup](https://github.com/Lakr233/vphone-cli/blob/67d0734a6f5ef960b9a12320b216e73d6491ed18/Documents/Guides/host-setup.md).

**HYPOTHESIS:** this is the user's preferred Phase 3 research environment because iOS userland/frameworks and debugger access can expose real loader/API differences that Catalyst hides. Successful executable mapping there would establish behavior only under its recorded patches. It cannot establish stock iOS admission, signing, sandbox or App Store feasibility.

**UNTESTED:** local VM boot, actual guest version, debugger attach/breakpoints, executable mapping/signature registration, guest dylib availability, Objective-C forwarding and Metal results. Phase 3 should record these independently. First stop at the smallest guest failing an admission check; preserve the error rather than changing security policy inside the runtime.
